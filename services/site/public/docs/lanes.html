Lanes and Landing

Agents work side by side without stepping on each other, and nothing lands until it’s been reviewed and checked.

A lane is one agent on one branch

When the orchestrator puts an agent to work, it opens a lane: one agent, in its own folder (a Git worktree) on its own branch, working through one or more related tasks in order. Separate folders mean agents never change each other’s files, or yours. The folder lives in Far Cooler’s own data folder on the runner, and the orchestrator removes it once the work lands.

A task has tabs for what it’s for, its agent, the changes on its branch, and its files.

Review

By default, a second agent reviews every change that isn’t trivial before it can land. Your charter can ask for more, such as a person’s approval.

How work lands

Ready lanes land together. Combining them first means they’re tested as they’ll run, side by side. The plan shows each group of lanes climbing three steps:

  1. Checking Here: the full test run, on the runner.
  2. Checking on CI: pushed, with CI running its checks.
  3. Landed: everything passed, and the work is on main.

If a check fails, the plan says so, and nothing lands until it’s fixed.

Straight to main, or pull requests

Your charter picks one. Straight to main suits a project you own. With pull requests, each change is a pull request a person approves, and the orchestrator never merges one without the approvals it needs. A protected main branch always means pull requests, whatever the charter says.
