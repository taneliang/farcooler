# A watch that tells you, and lets you answer

Spec 2 of three. Spec 1 put the fleet on a lock screen and a home screen; this
puts it on a wrist, and — the part that makes it worth building — lets you
answer an agent from there. Spec 3 adds reading transcripts and diffs.

## What is already true

Spec 1 shipped and is on this branch. The pieces this spec builds on:

- **The ladder.** The daemon derives `glyph`, `headline`, `line`, `rank` and
  `feed` per terminal, redacted and truncated on the host, explicitly so "a
  Mac, a phone and a watch must not each decide where the ellipsis goes".
  `rank` exists so "a watch complication cannot re-derive which of six agents
  matters most".
- **`FleetSnapshot`** in AgentKit: the ladder's fields plus `capturedAt`,
  `complete`, and per-agent `activityChangedAt`, with `confidence(in:at:)`
  answering how confidently a surface may speak. Pure Foundation.
- **`SnapshotStore`**: atomic read and write of one JSON file in an App Group
  named by the `FarCoolerAppGroup` Info.plist key, so it works in any target
  carrying that key.
- **The spike** (spec 1, Task 0) proved a watchOS target generates, builds and
  embeds correctly, and recorded exactly which settings are load-bearing.

## The one architectural decision

**The watch holds no SSH identity.** It asks the iPhone, and the phone — which
already has the Rust core, the runner keys and the live session — does the work
and answers.

The alternative was a watchOS build of the Rust core. It was rejected because
it needs a Rust tier-3 target, and because a watch that authenticates to every
runner is a second key to authorize everywhere and a second thing to revoke
when a watch is lost. The cost of the decision is real and must be stated on
screen rather than hidden: **with the phone out of range, the watch can show
what it last knew and cannot act.**

## What the watch is allowed to change

Read the fleet, dictate a prompt, reply to an agent that is waiting, and answer
a permission prompt. Nothing irreversible: no starting or stopping agents, no
committing, no discarding, no creating workspaces. A 45mm screen on a moving
wrist is the wrong place for a decision that cannot be taken back.

## Two targets

Both generated by `apps/ios/generate-project.py`, mirroring how the widget
extension is already built.

| Target | Bundle id | What it is |
| --- | --- | --- |
| `FarCoolerWatch` | `{BUNDLE_ID}.watchkitapp` | The watchOS app |
| `FarCoolerWatchWidgets` | `{BUNDLE_ID}.watchkitapp.widgets` | Complication and Smart Stack |

From the spike, the settings that are load-bearing and why:

- `dstSubfolderSpec = 16` with `dstPath = "$(CONTENTS_FOLDER_PATH)/Watch"`, on
  its **own** copy phase. The widget extension's `13`/`PlugIns` is a different
  slot, and using the wrong one fails at install or launch rather than at build.
- `PRODUCT_BUNDLE_IDENTIFIER` nesting under the phone app's, exactly as
  `.activity` does. A name that does not nest fails to sign against the app's
  profile.
- A `PBXTargetDependency`/`PBXContainerItemProxy` pair, or the app can embed a
  stale or absent watch app.
- `GENERATE_INFOPLIST_FILE = YES` plus
  `INFOPLIST_KEY_WKCompanionAppBundleIdentifier`. No checked-in watch
  Info.plist is needed — the phone target only has one because `UIAppFonts` has
  no `INFOPLIST_KEY_` equivalent, and the watch has no such key.
- **Not a generator concern, but it stops a build dead:** the build machine
  needs the watchOS **Simulator platform** (`xcodebuild -downloadPlatform
  watchOS`, several GB) before a `-scheme` build will start, even for a
  device-only build that never touches a simulator. It fails with no `error:`
  line, which reads like a project-generation bug and is not one. This belongs
  wherever build-machine setup is documented, and CI needs it.

## The transport

One protocol, `FleetClient`, with a WatchConnectivity implementation behind it.
The protocol exists because the watch's views must not know how the data
arrives — and because if a standalone core is ever built, only the transport
changes.

**State arrives by `updateApplicationContext`.** Latest-state-wins, delivered
opportunistically in the background, and a stale copy never queues behind a
fresh one — which is a snapshot's semantics exactly. The phone sends its
`FleetSnapshot` whenever the APP polls the fleet: `WatchLinkHost.send` is
reachable only from `FleetSnapshotWriter.write`, which only `Connection.refresh`
calls.

**Not "whenever it writes one", which this line said until Task 6 measured
it** — and the difference is visible on a wrist. The notification service
extension writes the snapshot too, which is the whole reason it exists: the
phone's widgets stay current while the app is closed. It *cannot* send it.
`WCSession` is unavailable to app extensions, so there is no call for it to
make and nothing reports the omission.

The consequence, which belongs written down rather than discovered on hardware:
**the watch and its complication are only ever as fresh as the last fleet poll
the phone app ran in the foreground**, while the phone's own widgets keep
advancing from pushes. A watch showing a two-hour-old fleet beside a lock screen
widget showing the current one is this, working as built, and not a bug.

It is not fixed here. A push-woken extension has no session to send on, so
closing the gap means the watch reaching the relay itself or the phone waking to
forward — both of which are a transport the watch does not have and a design
this spec deliberately does not carry. What the watch does instead is say how
old its fleet is, plainly, in the same `confidence(in:at:)` vocabulary every
other surface uses. Staleness a person can see is the honest half of a limit
that cannot be removed.

**Actions go by `sendMessage`,** which wakes the iOS counterpart in the
background if it is not running. Three, and only three:

```
prompt(terminal, text)              -> Sent | Failed(reason)
answer(terminal, request, option)   -> Sent | Failed(reason)
pendingPermission(terminal)         -> Permission | None
```

The phone performs each through the code paths that already exist — the
composer for a prompt, `{terminal, requestId, optionId}` for a permission — so
a watch and a phone cannot answer an agent differently.

**The watch's model is `FleetSnapshot` and nothing else.** It never decodes the
wire's `Terminal`. That is deliberate: the phone already projects the ladder
into a snapshot for the widgets, and a second decoder on the watch is a second
thing that can disagree with the daemon about the same pane.

## Three reachability states, never blurred

The rule that produces `LOST` everywhere else applies here too.

| State | What the watch shows | Actions |
| --- | --- | --- |
| Phone reachable | Live data | Enabled |
| Phone unreachable, snapshot present | The snapshot, with its age, said plainly | **Disabled** |
| Neither | An empty state saying the phone has not been heard from | Disabled |

A watch that offers an Allow button it cannot deliver is worse than one that
says it cannot reach the phone: the person walks away believing they answered.

## Answering a permission

A permission has an id and a set of options, and both come from the agent's
event stream rather than from the fleet — so the snapshot does not carry them
and the watch cannot invent them.

When the watch opens an agent whose status is `blocked`, it asks the phone for
that agent's pending permission. The phone answers with the id, the options and
the tool call, or with "nothing pending" — the honest answer when the agent is
blocked on something that is not a permission (a trust gate, a plain question).
The watch then shows the options the agent actually offered, by their own
names, rather than a hardcoded Allow/Deny pair. The daemon already declines to
invent that vocabulary and so does this.

If the phone has no live stream for that terminal, opening one is the phone's
business and not the watch's. The watch's request either comes back with a
permission or it does not.

## Screens

1. **Fleet** — rows of `glyph`, `headline` and `line`, ordered by `rank`. The
   ordering is the host's; the watch does not sort.
2. **Agent** — the headline, the signal line, elapsed time and `feed`'s three
   lines. This is where "what did it do while I was away" gets answered.

   **No subagent names**, which this line promised until Task 5 declined them —
   correctly, for a reason the spec should have caught. `FleetSnapshot.Agent`
   carries no subagent list; the wire has `glyph`, `headline`, `line`, `feed`
   and the rest, and nothing else. So the watch would have had to invent one,
   which is the ladder rule broken on the newest surface. What the host does
   send is the COUNT, already folded into `line` by
   `farcooler_core::feed::signal` ("3/7 · Designing test matrix · 2 agents"),
   and the screen renders that unchanged. Naming them means a new field on the
   projection every surface shares, which belongs on the host with the rest of
   the ladder rather than in a watch screen. The decline is commented at
   `AgentDetailView.swift:144`.
3. **Compose** — watchOS `TextField` gives dictation and Scribble for free.
   Sends by `prompt`.
4. **Permission** — the agent's own options as buttons, and what it is asking.

## The complication and the Smart Stack

A second watch target reading the watch-side snapshot: `glyph` for circular,
`headline` and `line` for rectangular, `rank` choosing which of six agents to
show. That last is the job `rank` was built for, and the reason none of this
requires the watch to think.

The watch app and its widget extension share an App Group on the watch, and
`SnapshotStore` already resolves its container from the `FarCoolerAppGroup`
Info.plist key — so it is reused unchanged, with the key stamped into both
watch targets from the same `FARCOOLER_APP_GROUP` build setting the phone
already uses. The container is per-device: the watch's copy is its own, fed by
`updateApplicationContext`, never shared with the phone's.

Staleness on the watch obeys the same `confidence(in:at:)` rule as every other
surface, including the prefix-not-suffix degradation spec 1 settled — a marker
that truncates away is worse than none.

## AgentKit gains watchOS

`Package.swift` grows a watchOS platform, but **that platform line is a
statement about the files the watch compiles, not a promise the whole package
builds for watchOS.** It does not, and this spec said otherwise before Task 1
measured it.

The blocker is not UIKit or AppKit — the package genuinely has neither.
It is `Account.swift`, which is built around `ASWebAuthenticationSession` at
seven sites; `ASWebAuthenticationPresentationContextProviding` and
`ASPresentationAnchor` are unavailable on watchOS, so
`xcodebuild -destination 'generic/platform=watchOS'` fails there. Guarding it
would be a change to the sign-in path, and sign-in is not something the watch
does — the watch has no account of its own and asks the phone for everything.

So the watch target **names the files it needs** rather than compiling the
package wholesale, the way the phone target already names its AgentKit sources
in `generate-project.py`. The set spec 2 needs is `WatchLink`, `WatchState`,
`FleetSnapshot` and `SnapshotStore` — FOUR, amended from the three this line
first named. `WatchState` moved into AgentKit rather than living in
`FarCoolerWatch/` because `swift test` cannot build a watchOS app target, so the
rule that a watch must never offer an action it cannot deliver had no test
standing behind it while it lived over there. It is verified to typecheck for
`arm64_32-apple-watchos26.0` and confirmed by a built binary carrying both that
slice and `arm64`. Spec 3 adds `Transcript`, `DiffComputation` and
`MarkdownView`, and should re-measure rather than assume.

`AgentActivityAttributes` is deliberately **not** in that set, though an earlier
draft of this line listed it. It is `#if os(iOS)` guarded end to end, so on
watchOS it compiles to an empty translation unit — naming it would buy a build
id and a sources-phase entry that assert a dependency the watch does not have,
and would tell the next reader of `WATCH_AGENTKIT_SOURCES` that the watch
renders a Live Activity. It does not; ActivityKit has no watchOS counterpart.

## Verification

Pure tests, which is most of the value and needs no device:

- `FleetClient`'s request and reply types round-trip through the dictionary
  representation `WCSession` actually carries — a payload that fails to encode
  is an action that silently never happens.
- The three reachability states are distinguishable, and actions are disabled
  in two of them.
- A permission reply names an option the agent actually offered.
- A generator test asserting the watch app is embedded at `dstSubfolderSpec 16`
  / `Watch`, that its bundle id nests, and that both watch targets carry the
  App Group key — the spike named all three as load-bearing and each fails
  after build rather than during it.

Then a device, for everything WatchConnectivity actually does.

## Risks

1. **Cold-phone `sendMessage` latency.** Waking a backgrounded iOS app and
   getting an answer has never been measured here. If it is slow, the compose
   and permission screens need a progress state that says what is happening
   rather than appearing hung. This is the same unknown that deferred answering
   from the lock screen in spec 1.
2. **`updateApplicationContext` cadence.** It is opportunistic by design, so a
   watch snapshot can be much older than a phone one. The staleness rules
   already handle saying so; what is unknown is how often it actually lands.
3. **The watch app's own lifecycle.** A complication does not run the app, so
   the snapshot it reads is only as fresh as the last context the watch got.
4. Everything install-time from the spike remains unproven: whether a real
   paired watch accepts the companion relationship, and whether provisioning
   nests correctly for two new bundle ids.
