## Retry behavior

- The retry workflow still handles main-push CI. A runnerless cancellation qualifies when GitHub's check annotation confirms acquisition failure. A copied cancellation can recover its annotation from a runnerless cancellation with the same job name and completion timestamp. The retry uses the current job ID and prioritizes older unserved jobs when more than one qualifies.
- Automatic acquisition retries stop after **eight CI attempts total**, including the original and any manual attempts. The existing first-attempt retry for actual test failures uses the same submission path. After the ceiling, a cancelled required job leaves CI non-green.
- The primary controller and its recovery workflow share a concurrency group for the source attempt. Each controller has **three submission rounds**, with a fresh source read before each POST and ten seconds between rounds. If the POST succeeds, the controller continues checking for the rerun without submitting again. If the POST times out or returns an error, the next read can still confirm that GitHub queued or started a rerun. An accepted or manual rerun advances the source run, which also stops duplicate deliveries. Pre-POST artifacts are ignored because they only show that a request was planned.
- A failed or cancelled primary controller triggers **one independent recovery workflow**. The board and engine watch both controllers by exact source run ID and attempt. The 15-minute delivery grace starts at CI completion for the primary controller and at primary controller completion for recovery. An observed queued or running controller keeps CI pending through the original landing deadline. After recovery completes or its delivery grace expires, CI can settle if a fresh read still shows the same completed attempt. The landing records the terminal reason and names the job that never acquired a runner when its record is available.
- The Python regression replays the app build's copied cancellation from attempt 2. It exercises repeated rejected POSTs, recovery of the same job ID, and a recovery POST that times out after GitHub has already queued attempt 3. The original pre-POST marker replay failed because the marker suppressed selection. The daemon regression follows a failed controller through recovery past the original landing deadline, and checks that terminal failure records why.
