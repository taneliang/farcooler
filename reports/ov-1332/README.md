# ov-1332: Rust compilation in landing gates

First, trial a **trusted, bounded sccache for dependencies**, with isolated per-fold targets and clean-versus-cached validation. Expect 0–4 minutes off these gates, not a measured promise; prove hit rate and wall time before adoption. A persistent shared Cargo target is less attractive: this repository already observed cross-checkout stale artifacts. Neither Cargo fingerprints nor a cache key alone protects against a malicious cache writer.

## Where the output lives

The service opens its engine under `<app root>/workflow` (`crates/daemon/src/workflow_service.rs:25`). A group's `item_tree` is `workflow/tree-wf1-<digest of workspace,item>` (`workflow_runtime/adapters.rs:183-195`); the fold removes any existing tree at that name and creates a new Git worktree at the base (`workflow_runtime/coding_verbs.rs:539-557`). The configured gate runs with that tree as its working directory (`workflow_runtime/coding_execute.rs:423-435`); `lane-gate.py:688-702` runs steps in the checkout unless a step specifies another directory. With no target override, Cargo uses `<fold tree>/target`; the wrapper and archive explicitly use `target/` (`scripts/landing-gate:22`, `scripts/lane-gate.py:1274-1275`). `base_env` inherits the environment (`lane-gate.py:840-856`), so a deliberately configured `CARGO_TARGET_DIR` can alter Cargo's location; path-assuming scripts also need adaptation. The engine pins its own process context (`coding_execute.rs:337-354`), not a shared target.

**Different landing groups do not receive a previous group's target in the current source.** A new fold starts with a new checkout and no ignored `target/`, subject to an explicit external override. Within a gate, successive commands do share its target, and retry/recovery is not necessarily cold: `settle_run_tree` uses `git clean -fd`, which does not remove ignored output (`coding_execute.rs:368-388`, `.gitignore:1`). The landing wrapper passes `--keep-target`, and `lane-gate.py:1036-1037` also excludes `--landing` from its ordinary green cleanup; the comment at `scripts/landing-gate:30-31` promising a handoff is obsolete. The engine instead releases configured build folders when eligible, retaining source and refs (`fold_trees.rs:1-15`, `build_cleanup.rs:64-115`); cleanup can skip or retry, and is not the reason a new fold is cold.

The `workflow/build-wf1-b227332ab03d668443dafe47f4d3ed46120ac211c4f3e90999ae4e8d006cb099` on this host is a **leftover parked target**, not the current gate target. Historical `git show 5253f9945^:crates/daemon/src/workflow_runtime/fold_trees.rs` lines 1–14 and 21–55 identifies the repository-keyed `build-wf1-*` path and the former rename/restore handoff; commit `5253f9945` replaced that machinery with output release. A read-only `du -sh` today found 26 GiB `debug`, 783 MiB `rust-tests.tar.zst`, 1.0 GiB iOS simulator, 782 MiB Android, 420 MiB wasm, 285 MiB release, and smaller files: roughly 30 GiB of old Rust and gate outputs. Its mere existence does not mean it is reused. Do not infer the contents or provenance of every similarly named folder from this one.

## Ranked choices

Estimates are hypotheses per landing, non-additive and capped by that 7.6–8.4 minute observed gap. They require a controlled warm/cold measurement under the same gate load. Retain every gate command and test.

1. **sccache, isolated gate target:** 0–4 minutes; start with a 10–20 GiB bounded local cache *in addition to* the per-gate target (historical lane targets 10–84 GB, `scripts/heavy_lock.py:86-99`); actual working set and hit rate are unmeasured. Disable incremental compilation for the cache trial and measure its cost: sccache cannot cache incremental builds (`heavy_lock.py:92-96`), and linking, build scripts, unsupported invocations and workspace changes can still dominate. Use a gate-owned cache namespace with no builder or untrusted writer, secure permissions, compiler/target/flags and input-sensitive keys, and integrity-checked atomic entries. Invalidate on toolchain/config changes or suspicious state; cache failure falls back to compiling, never a passed gate. Compare repeated clean and cached gates including test inventories and outcomes. Content addressing does not authenticate an attacker who can write the cache; access control and trusted population are required.
2. **Persistent gate-owned target:** 0–4 minutes, roughly 10–30+ GiB retained per key plus active output and capacity for concurrent groups; observed old parked tree is ~30 GiB, not a sizing guarantee. Key by repository, toolchain, lockfile, host/target, profiles, flags and relevant configuration; those keys are necessary, not sufficient for source correctness. `heavy_lock.py:89-93` records a real shared-target mtime failure across checkouts. Do not simply share or copy fingerprints across fresh checkouts. Serialize ownership, isolate concurrent outputs, force workspace units and build scripts to rebuild against the exact fold (including generated and native inputs), and let Cargo validate dependencies; discard on uncertainty. Protect the directory from untrusted writers, verify provenance and periodically compare clean gates. A fixed source path or verified content-based invalidation needs design and testing before this is safe.
3. **Seed from a builder's artifacts:** 0–2 minutes, potentially another 10–30+ GiB for an isolated copy, with copy time and lost sharing reducing savings. Builders may have compiled different features, profiles and source than the combined folded candidate, and their output can be modified by the agent; normal builder cleanup may already have removed it (`builder_resources.rs:24-48`). Treat it as untrusted: do not import binaries or fingerprints as gate proof. Only promote dependencies from a separately trusted, isolated build with authenticated provenance and content validation, rebuild all workspace units and build scripts from the fold, and compare to clean runs. That effectively becomes option 1 or 2 with more complexity; copying an arbitrary builder target is not safe.

No gate, build, or test was run for this research.
