# ov-1360 · See the engine at work

Add **Engine** as a workspace destination off Plan. On Mac, start with **A · Stations**. It answers where a ticket is and why it stopped in the same place, while the adjoining cards show whether landing or agent capacity is involved. A Plan run note or landing card can open Engine focused on that ticket or group. Reuse the same projection for a single-column phone view and for the web after Mac ships.

## Layout options

All four mock-ups use the same Nov 19 evidence. The Mac layouts are 1,440 px wide and the phone layout is 390 px wide. They show the full scrolling content. Each is a dark appearance study.

| Option | What is visible | Trade-off |
| --- | --- | --- |
| **A · Stations** | Tickets and their reasons are grouped in workflow order. Landing checks and agent activity are alongside. The capacity strip stays above the work. [Mac mock-up](mac-a-stations.png) | The least navigation for ordinary diagnosis. A long Build queue can push Review and Join down. Keep station disclosures and scroll to a selected ticket from Plan. Show the first actionable reason on the row and let users disclose the full evidence. |
| **B · Station navigator and inspector** | Station index on the left, compact ticket list in the center, and the selected run's evidence on the right. Landing and agents stay available in the inspector column. [Mac mock-up](mac-b-inspector.png) | Better for comparing many runs at one station and reading long logs. At narrower widths the inspector competes with the list. Only one selected run gets a full explanation at a time. |
| **C · Activity** | A station index shows where work is now. Below it, the reverse-chronological feed connects send-backs, session losses, and landing changes to their subjects. The landing and agent cards remain alongside. [Mac mock-up](mac-c-activity.png) | Best for reconstructing an incident from a time window. Quiet work can fall off the feed even when it is still blocked, so current failures and station membership also need a persistent place. Routine polling would bury significant events unless the projection filters them. |
| **Phone · Stations** | Capacity first, then station sections and landing and agent cards. Jump links lead directly to Stations, Landing, and Agents. The runs wrap their reasons in full at phone width. [Phone mock-up](phone-stations.png) | A single scroll works with long text and larger type. Users lose the side-by-side view, so each landing and agent entry keeps the ticket or group key and its timestamp. |

Use A as the main destination and put a focused run or group detail one selection away. Give the detail the evidence treatment illustrated in B. Use the logged event order from C inside a run or group history when it helps explain a transition. A separate activity destination can wait until operators need cross-ticket incident history often enough to justify it.

The Mac options follow ov-216's frosted window plane, opaque content cards, quiet inset output and spacing between groups. Selection uses the app's accent wash. Amber marks waits that need attention and red marks failures or lost sessions, each with a text label. Keep the app's system toolbar and scroll-edge treatment. Use system type, monospaced technical output, and native keyboard focus on Mac. On phone, keep full-width row targets and let titles, reasons and logs wrap at larger text sizes. Preserve the distinction between local checks and GitHub CI in both the visible and accessibility labels. The mock-ups approximate the system materials. ## Shared Rust projection

Add a read-only `crates/client::engine_view` projection alongside `workflow_presentation` and `plan_view`. Adopt their existing status, reason, ID, navigation, and style types where they fit. Bridge the same semantics to Swift, Kotlin, and web using the existing client presentation boundaries. The app owns selection, disclosure, sizing, and formatting for locale and time zone. Rust owns membership, ordering, state and reason precedence, status labels, and the relationship between a run, its agent and any landing or gate evidence.

| Output | Fields and derivation |
| --- | --- |
| **Engine view** | Workspace and runner identities, workflow epoch and revision, runner sample and event cursors, source timestamps, connection state, ordered stations, runner capacity, agents, and recent landing attempts. Keep current and historical records explicitly tagged. Use stable IDs in lists so refresh preserves selections and scroll position. |
| **Station and ticket** | Station ID, label, kind, queue order, optional occupancy/limit, and separate working, queued and held entries. A ticket row carries its key, title, station, current run/effect identity, state and time, typed reason, send-back allowance and references to its agent or batch. Resolve today's station from the run's pinned definition and step ID, using the published layout for display order where IDs match. Add a still-active unmapped station with its own label when a legacy pin differs. Use authoritative queue order when available and a stable order within other groups. A joined ticket lives under its batch. Do not duplicate it in the station totals. Future engine input can project ordered stations and retired stations directly. [Station and queue model](../../docs/engine-pipeline.md#4-stations) |
| **State and budgets** | Distinguish running, awaiting a decision, queued for a resource, held, failed, uncertain, and closed. An admitted effect can still be held or paused, and a pending or claimed effect does not establish that its agent started. Use the explicit failure/stop or admission reason for the matching run, then the decision principal, dependency or queue evidence. Show an unknown reason when evidence is absent. Preserve the previous failure separately from the current wait after a send-back. Compute remaining as `definition.send_back_limit().saturating_sub(sent_back.len())` with the conversion bounded to the type. Keep unavailable, zero, and any future unlimited policy distinct. Send-backs, retries and CI reruns have separate counts. [Workflow projection](../../crates/client/src/workflow_presentation.rs) · [Budget implementation](../../crates/workflow/src/definition.rs) |
| **Landing attempt** | Stable group and attempt IDs, member ticket keys, base and pushed commit refs, ordered checks, per-check state/time and optional completed/total counters, bounded gate output excerpt and an authorized log reference. Carry CI separately with commit or run identity, status, last observation, known jobs and an authorized link. After a split or retry, keep old output attached to its attempt. Show the current check and elapsed time when the runner lacks a denominator. Historical CI must match the pushed SHA and, when known, provider run/attempt. [Landing queue projection](../../crates/client/src/plan_view/landing_queue.rs) |
| **Capacity** | Scoped station, workspace and runner pool limits when available, used counts, this workspace's holders, anonymous elsewhere count, queue position, and typed blockers such as disk, load and cooldown. An observed metric carries its unit, value, sample time and applicable threshold. Report an active hold only when the scheduler or adapter declares it. A historical disk refusal stays in the attempt that received it. Keep unavailable readings distinct from zero and stale readings distinct from current ones. [Runtime slots](../../crates/daemon/src/workflow_runtime/places.rs) · [Load and admission](../../docs/workflow-scheduling.md) |
| **Agent** | Agent or session identity, role, harness, reported model when known, resolved run/effect identity, explicit session state, and last timestamped activity with source. Requested or selected model is labeled when it is the only evidence. Show the latest engine-observed start, turn, pause, stop or loss. Allow a last known activity to remain visible when disconnected. Record losses against the exact sessions, even when a retry starts a new session for the same ticket. |

### Data path and rollout

1. Read the authorized workflow snapshot, Plan ticket titles and landing data. The daemon's full workflow read already provides state, stop reasons, process log metadata and `places`. Its summarized read drops per-item definitions and terminal landing groups, and the client's existing snapshot wrapper does not project places. Add a bounded Engine summary that carries the required facts and recent attempts. Avoid moving full definitions, receipt files, or agent transcripts to each app. [Daemon read path](../../crates/daemon/src/workflow_runtime/wire_commands.rs) · [Client snapshot](../../crates/client/src/session/workflow.rs)
2. Extend observability at the daemon boundary for explicit per-run admission and pause reasons, timestamped load and disk samples, live gate/check progress, and typed agent activity keyed by effect/session. Read available CI through the existing board source and fetch gate excerpts or more history on disclosure via an authorized endpoint. Produce plain-text excerpts with secrets and terminal controls removed. A blocked or slow auxiliary read must not prevent rendering the core snapshot.
3. Use workflow changes to invalidate current state. Capacity, CI and agent observations can change without a workflow revision, so track per-source cursors or use bounded refresh while Engine is visible. Drop older observations within each source, discard mismatched workspace/epoch/run data, and resnapshot after reconnect. Preserve last known values with a visible timestamp and stale label. Keep other workspaces' tickets and agent identities out of runner-wide counts.
4. Ship the Mac read-only destination first. Keep retry, resolve, send-back and workflow editing in their existing authorized views, reachable by opening the subject. Then render the same projection on phone and web. Add projection fixtures for the evidence above, legacy/missing samples, an in-progress gate with unknown total, CI for the wrong commit, a lost agent followed by a retry, and a queue blocked by disk, load or a full pool. Verify keyboard navigation, large text, light/dark and the corresponding contrast and transparency settings when implementing the native views.
