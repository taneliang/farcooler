## Durable intent/recovery behavior

Swift's single AgentKit adapter serves both Apple apps; Kotlin and browser adapters implement the same finite journal lifecycle. Storage is private to the application/origin and namespaced by actual authenticated host/workspace/account (signed-in user, or the existing authenticated device/local user identity where applicable). It does not persist raw State, capability authority or credentials.

Versioned envelopes checksum the payload with SHA256 and validate explicit Preparing/Prepared/Complete/Abandoned phases. Preparing is persisted before one prepare invocation. Opaque Prepared is persisted before every first submit; preparation or persistence failure prevents submission. Accepted/discarded replies retain the same prepared identity and immutable inner JSON. Each explicit retry invocation sends at most one submit under the existing Session deadline, with a persistent audit count; later explicit retries are not permanently banned after three attempts. Refresh, reconnect, view close/open and restoration never replay a mutation or prepare.

Only an integrity-valid Preparing marker with no Prepared, no result and zero submission attempts can use **Reinspect Unsubmitted Action**. It explicitly reads a fresh authenticated snapshot, marks that proven never-submitted entry abandoned, and requires a subsequent user selection for a new intent. Prepared entries cannot take this reset path. Corrupt/ambiguous data fails closed. An unknown accepted intent is never reprepared.

Browser Web Locks serialize preparation/retry across tabs. Apple main-actor ownership and Android's shared adapter/mutex serialize views. Native writes are atomic (Android also syncs the file before rename). All adapters preserve results in the originating namespace, recheck current identity across relevant awaits and resolve the current core for retry. This is process-restorable application storage, not an adversarial local-storage authorization boundary or a power-loss durability claim.

The reviewed generation/selection/run-identity result fences and keyboard focus behavior remain. Retry explicitly navigates to its retained item; results cannot be attached to a replaced run. A real browser close/reopen exposed an additional delayed old `close` event disconnecting the new sheet; `workflow-view.ts` now ignores that event while the dialog is open. The original focus/lifecycle suite and real Enter-key checks still pass.
