All three can share the compiled TypeScript UI, styles, xterm renderer, and Rust projections and protocol. The current UI calls `WebRunner` and `WebPane` from Rust/WASM. A local adapter needs to offer their UI-facing operations, including separate control and output paths, streaming and close. The existing native client can connect to the Unix socket, but its browser-used `open_stream` helper opens an SSH channel. Local mode needs a sibling socket or stdio session for pane output. The hosted path retains Worker, Tailcat, SSH and passkey admission. Native integrations require host code and a small UI capability surface as they are introduced. The prototypes measured only the terminal screen and echo adapter, so there is no credible line count for the full local adapter. ### Session authority

The daemon binds a `0600` Unix socket under a `0700` directory. The regular listener uses the kernel-reported PID for caller attribution. A direct local connection currently receives `host_admin` based on access to the owner socket. Root and processes acting as the owner are inside that trust boundary. A valid protocol hello by itself establishes compatibility. A browser renderer or remote page must never be able to turn an unauthenticated request into the broker's owner session. [Unix listener](../../crates/transport/src/listener.rs), [daemon admission](../../crates/daemon/src/main.rs).

- **Browser.** Keep the adapter loopback-only and use an exact allowlist for the listener's Host and WebSocket Origin. Use a single-use launch credential exchanged for an expiring per-browser session, CSRF protection for HTTP mutations, and session checks at WebSocket upgrade. Bind the granted commands to the authenticated session. Browser network policies and CORS alone do not supply authorization.
- **Electron and Tauri.** Admit each bridge session from the app-owned top-level renderer, pin it to the packaged origin and window, and keep core handles in the host. Bind each session to a daemon-enforced scope and revoke it when the view closes or navigates. Validate commands and resource IDs. Electron needs a dedicated packaged-asset origin, context isolation, a sandboxed renderer with Node integration disabled, sender validation and navigation restrictions. Tauri needs window-scoped command capabilities and permissions for custom commands, with remote origins excluded. Keep any arbitrary web content in a view with zero bridge access. [Electron security](https://www.electronjs.org/docs/latest/tutorial/security), [Electron protocols](https://www.electronjs.org/docs/latest/api/protocol), [Tauri capabilities](https://v2.tauri.app/security/capabilities/).

**No option prevents a user from deliberately bridging their Unix socket or sharing a session.** The desktop choices remove the ordinary HTTP forwarding path. A process with access to the owner's account or a user who intentionally shares credentials, control or terminal output can expose the same authority. The Unix socket is an OS-account boundary and does not prove which executable opened it.

Use an argument vector without a shell and select an explicitly configured distro, Linux owner and installed binary. Keep stderr separate from stdout, which carries framed bytes. Authenticate each session in the core and keep the same capability and resource checks over stdio. The current `--stdio` mode can open a second service if the daemon is absent. Local mode needs to connect to the owning daemon or report it is unavailable, since opening an independent service gives a different view of live state. A terminal needs a control session and a separate `terminal.attach` stream session to preserve the existing framing, replay and backpressure. For Windows proof, start the registered WSL daemon, open a real pane, verify replay, input and resize, then stop/restart the distro and reattach. Capture listener tables on both sides, test with WSL localhost forwarding disabled, and record the distro, Windows build and WSL version. Keep default Linux paths in the distro and translate only for an explicit Windows editor handoff. A Linux shell under WSLg could use the Unix socket directly if WSLg is supported on the installed Windows version. That is a separate packaging choice. ## Browser boundaries from ov-1439

“Can remove” means the host can supply the capability behind an explicit grant. It does not come for free with an app window. [Inventory boundary definitions](../ov-1439/parity.md#browser-boundaries).

| Boundary | Browser + loopback | Electron | Tauri |
| --- | --- | --- | --- |
| **B1 · Local files and clipboard** | Partly. Authenticated core can browse paths on its own host. Browser upload, clipboard and native selection remain constrained. | Native picker, rooted path handoff and clipboard via the host. Finder selection or equivalent needs platform integration. | Same through scoped Rust commands and native pickers. |
| **B2 · Local services, tools, native apps and updates** | Partly. The adapter or CLI can perform scoped core-host tasks. The tab relies on external installation and OS handoffs. | Host can launch a configured editor and handle setup and app updates through native APIs and packaging. | Same with Rust commands and OS/package integration. |
| **B3 · Dragging** | In-page splits and drag/drop stay available. Browser payloads constrain cross-app file drops and native window placement. | Native window drag and file paths from desktop drops can be handled. OS policies still apply. | Same where the system webview and desktop compositor support it. |
| **B4 · Shortcuts and windows** | In-page remapping and focus only. | Native window management and global shortcut APIs, subject to OS/compositor support. | Same through native APIs/plugins, with platform testing. |
| **B5 · Embedded sites** | Page framing and cross-origin rules stay in force. External tabs handle arbitrary sites. | A separate top-level child view can avoid iframe restrictions for compatible sites. Preserve origin isolation and withhold the app bridge. | A separate webview can do the same. Use an external browser for sites that reject embedded webviews or require a full browser context. |
| **B6 · Closed-tab notifications** | Requires Web Push or a separate native notifier. | A running host can subscribe and issue OS notices with the window closed. Fully quit still requires a background agent or push mechanism. | Same, with OS notification integration. |
| **B7 · Direct runner access** | A trusted adapter can reach its local core or offer scoped SSH operations. The browser itself remains behind that adapter. | Host can reach Unix sockets or WSL pipes and later use configured SSH with normal auth and host verification. | Same via the Rust host. |

## Recommendation and first ticket

Recommend a listener-free desktop shell for local mode. Start with **Electron** for the first transport slice. Its bundled Chromium gives the terminal a common engine across the first desktop targets, at a material download and update cost. Both shells passed Canvas rendering on both hosts. In the Ubuntu guest, Electron had the lower loaded input p95 of the two shells. Keep Canvas as the default. Tauri is the smaller distribution candidate if measurements on supported Linux desktops confirm acceptable input latency. The loopback option would serve the local UI over an IP port and would require maintaining a second browser-to-core authentication boundary.

**First ticket · Owner-only terminal attach over local desktop IPC.** In a dev build on macOS and Linux, load the shared web terminal screen in a sandboxed Electron window and use a narrow host adapter to attach one existing pane through the owning daemon's Unix socket. Prove scoped session admission and rejection from an unrelated renderer, replay, ordered input, resize and reattach, and zero shell listeners for the UI or core. Keep the hosted transport in its existing entry point. Defer packaging, native actions and Windows support. Verify the existing stdio bridge over `wsl.exe` on real Windows before committing to Windows support.
